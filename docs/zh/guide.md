# 使用说明

这份说明面向第一次使用的人，覆盖安装、第一次配置、日常流程、权限和常见问题。更深的实现细节看 [文档索引](../../README.zh-CN.md#文档)。

## 0. 先确认它适不适合你

适合：

- 你每天有大量零散的事，需要有人替你记住、跟进、整理，而不是每件都自己开一个聊天窗口。
- 你已经有 DeepSeek Harness，愿意让 Agent 在本机长期运行。
- 你接受「先给一个小范围的授权，看它做几件事，再慢慢放开」。
- 你的工作主要围绕 GitHub、飞书、文档和本地文件。

不适合：

- 你想要一个开箱即用的 SaaS，不想装环境。
- 你需要多个人同时使用、审批和审计。
- 你不能让电脑长期开机联网。
- 你想让 Agent 完全自动地对外发消息、改生产系统、花钱。这个项目默认不允许这些事。

## 1. 安装前准备

需要的东西：

- Node.js 22.19+ 或 24+
- pnpm
- git 2.32+
- Python 3.8+
- tmux（Linux/macOS）
- 一个可用的 DeepSeek Harness，并且已经配置好模型服务
- 如果用 GitHub 来源，`gh` 2.48+
- 如果用飞书来源，`lark-cli` 和一个已发布的飞书应用

Windows 上还有几条额外的注意点，见 [Codex on Windows](../009-codex-windows.md)。

**不要让两个实例监听同一个飞书群或同一个状态目录。** 状态目录有锁，并发启动会失败或互相干扰。

## 2. 安装

### 2.1 推荐：让 Agent 帮你装

打开 Codex、DSH 或其他能读写本机的编码 Agent，把仓库地址和下面这段话给它：

```text
帮我安装这个项目：https://github.com/ShengrenHOU/EnyAgentDesk

先读 INSTALL.md，按里面的步骤装。安装用一份 enyagentdesk.install.json 和一条命令。
中间需要我创建账号、登录 CLI、提供模型密钥或飞书群的，停下来把命令给我，我自己执行。
装好以后跑 self-check，把失败项和下一步告诉我，再问我平时想把哪些事交给它。
```

它会先探测环境，再一个问题一个问题地问你。所有问题答完，它会给你一份完整计划，确认后才开始安装。GitHub 和飞书两个来源都会接上；单个来源不在这个安装流程里。

### 2.2 手动安装

```sh
git clone https://github.com/ShengrenHOU/EnyAgentDesk enyagentdesk && cd enyagentdesk
cp examples/install.minimal.json enyagentdesk.install.json
# 填写 enyagentdesk.install.json；每个字段的含义见 INSTALL.md

node scripts/install.mjs --config enyagentdesk.install.json --dry-run
node scripts/install.mjs --config enyagentdesk.install.json
node scripts/self-check.mjs --config enyagentdesk.install.json
```

安装器负责建 profile、装 bundle、写机器配置、启动服务，并通过本机管理 API 保存 GitHub、飞书、允许名单和执行器设置。配置里不存任何密钥；GitHub、飞书和模型密钥都留在你自己的 CLI 或环境变量里。

已有 profile 的手工安装、配置和启动方式见 [006 Deployment](../006-deployment.md)。安装范围与限制见 [INSTALL.md](../../INSTALL.md#6-limits)。

### 2.3 Windows

Windows 上建议使用 Node 24、固定版本的 DSH 和与本机桌面应用一致的 Codex 可执行文件。完整步骤见 [Codex on Windows](../009-codex-windows.md)。

如果只是前台排查，可以用仓库里的 `scripts/start-windows.ps1`。它需要 DSH home、DSH CLI 和 Lark 配置目录三个绝对路径，参数说明见 [Codex on Windows](../009-codex-windows.md)。

如果你要长期运行，建议使用仓库里的启动器加计划任务，不要直接 `node` 起进程。启动器会做端口占用检查、启动锁、密钥注入和 PID 回执。

## 3. 第一次配置

打开面板的 **设置**，按顺序配。

### 3.1 来源

- **GitHub**：填仓库 `owner/name`、Agent 账号的 `gh` 包装器路径、允许的账号。Agent 账号最好不要用你本人的账号，它写的每条评论都会以这个身份出现。
- **飞书**：填 `lark-cli` 路径、要监听的群、每个群是「接收全部消息」还是「只接收 @」、是否接收私聊。建议先只开一个私密群。
- **微信**：只读，依赖本机已经授权的聊天记录。它不会主动发消息。

每个来源都有开关。关掉来源不会取消已有的工单，只是不再接收新事件。

### 3.2 谁可以发起工作

这是最重要的一步。每个来源有自己的允许名单。在默认准入设置下，名单为空时，没有人能通过这个来源发起工作。

但这不是无条件的。如果某个接收范围的「名单外 · 点名智能体」被改成「明确的请求」，名单外的人只要 @ 一下 Agent，仍然可以发起工作，`observe` 模式也一样。要真正关死，除了清空名单，还要把这个范围的这一格改回「忽略」，或者关掉来源。

建议：

- 第一版只放你自己，或者你完全信任的一两个同事。
- 飞书群可以设为「只接收 @」，这样普通聊天不会触发工作。
- 主动接单先设成 `observe`。它会记录「如果放开，它会接哪些活」，但不真的接。
- 看过一段时间的 observe 记录，觉得判断没问题，再改成 `auto`。

### 3.3 执行器

- **DSH 执行器**：使用 DSH 原生会话，适合大多数任务，配置最少。
- **Codex 执行器**：使用本机 Codex App Server，适合需要更强代码能力或特定模型的任务。需要填 `codexCommand`，并保持 Codex 版本和桌面应用一致。

两种执行器共享并发上限。配置 Codex 后，新工单还可以按文档、研究、实现、辅助四类路由，或者显式指定模型。

执行目录建议每个工单一个子目录。`prepare` 命令可以用 `git worktree` 把仓库检出到 `$DSH_SUPERAGENT_DIR`，这样每个工单有独立的代码副本，不会互相踩。

### 3.4 模型

面板里的研判模型和执行器模型是分开的。

- 研判模型负责理解你的话、判断接不接、路由到哪个执行器。
- 执行器模型负责真正干活。
- Codex 的模型由本机启动配置决定，面板里的 DSH 模型选择不适用。改 Codex 模型后需要重启运行实例。

### 3.5 网络

如果你的网络需要代理才能访问 GitHub 或模型服务，在 **设置 → 执行** 里填出站代理。执行器命令和本机的 `gh`、`git`、`lark-cli` 都会走这个代理。留空表示直连，并清除启动环境里继承的代理。

## 4. 日常使用

### 4.1 讨论和交办

主控对话是日常入口。你可以先讨论，讨论不会自动变成工单。只有明确的交办才会。

一个好的交办包含四件事：

- 要做什么，做到什么程度算完成。
- 哪些事不要做，哪些边界不能碰。
- 有没有必须遵守的规范、链接或资料。
- 如果卡住了，希望它怎么找你。

例子：

```text
帮我审一下这个 PR，重点看它有没有改变对外的数据口径。
只读，不要评论、不要合并、不要改代码。
如果发现需要产品决定的地方，把问题和两个可选方案一起给我。
```

### 4.2 看进展

工作台首页有四块：

- **当前重点**：它根据已有工单和来源动态整理的推进建议，每条都带依据。
- **需要你**：等你决定或验收的事。
- **持续事项**：正在跑和等待中的工单。
- **最近成果**：过去 24 小时的交付。更早的在完整历史里。

普通进展不会来打扰你。想看细节，点开工单看执行记录、报告和交付物。

### 4.3 回答决定

当它需要你拍板时，会提一个具体问题，通常带两个或三个选项，也会说明为什么需要你定。

回答时直接说结论，必要时补一句理由。答案会回到原工单，不需要重新描述背景。

### 4.4 验收和返工

成果会以链接或文件的形式回到原对话。验收时看三件事：

- 它声称做了什么，和实际改的是不是一回事。
- 它跑了哪些检查，哪些没跑。
- 有没有把「未验证」说成「已验证」。

要返工就在原工单上提，不要新开一件事。这样历史、授权和执行会话都能接上。

### 4.5 停止和继续

- **暂停**：当前回合可以做完，后续输入和新的执行阶段先不开始。
- **停止**：当前派工结束，授权收回。之后同一个话题里的新消息不会自动恢复它。
- **继续**：在工单的完整记录里选择继续，补充新的要求。历史、工作目录和已完成的成果都保留。

### 4.6 定时跟进

你可以让它在一个时间点之后回来复查，比如「明天早上九点看一次对方回没回」。它会结束当前回合，到点再唤醒同一个工单，不会一直占着执行器。

不需要的跟进可以取消。

## 5. 权限与安全

这个项目的安全边界不是「模型不会做坏事」，而是**授权、范围和人工控制**。

- **谁能发起**：每个来源的允许名单。名单外的人点名 Agent，默认也不会直接接单。
- **能做什么**：接单时记录的授权范围。范围越大，越需要你明确说。
- **不能做什么**：禁止调用的命令、只读模式、`observe` 模式、需要人工确认的合并。
- **怎么停**：暂停、停止、结束工单。停止会收回授权。

另外几条实践：

- 不要把管理端口暴露到公网。默认只监听本机。
- 不要把 API key、bot secret、登录态写进仓库或提示词。
- 重要操作保留回执。Agent 说完成了，不等于线上真的生效了。
- 定期看「需要你」和失败的工单。沉默不代表没问题。

## 6. 运行与恢复

- 状态在 SQLite 里，执行目录在 `stateDir/work` 下。升级前备份。
- 重启会恢复工单和执行器绑定。正在跑的一轮可能需要先核对结果，再重试。
- 不要为了重启去删状态锁、删数据库或杀掉桌面应用。
- 结果不确定时，先看执行器自己的会话记录和外部系统的实际状态，再决定是否重试。
- 一个工单可以换执行器，但要求它当前空闲，并且交接内容完整。

## 7. 常见问题

**它和普通聊天 Agent 有什么区别？**

普通聊天以「这一轮回答」为单位。它以待办的工单为单位，记得授权、进展、等待条件和交付物，能在你离开后继续。

**需要一直开着电脑吗？**

需要。它是本机工具，不是云服务。电脑睡眠、关机或断网，正在跑的工作会停。

**会不会乱花 token？**

不会一直轮询。等待人工决定时，工单是挂起的，不占执行器；定时跟进也是到点才唤醒。真正的成本来自执行器实际干活的轮次。

**会不会自己乱发消息、乱合并？**

默认不会。主动接单可以先只观察；对外写操作、合并、部署都需要对应的授权和门禁。第一次用请把允许名单设小。

**支持 macOS 和 Linux 吗？**

代码和测试覆盖 Linux/WSL，部署文档主要按 Linux 写。日常使用验证目前以 Windows 为主。macOS 没有专门验证。

**支持多个仓库吗？**

支持。GitHub 来源可以配置多个关注仓库；每个工单仍然有自己的目录和授权。

**能在手机上用吗？**

不能直接打开面板。飞书可以作为交互入口，但完整的工作台目前是桌面浏览器。

**面板打不开怎么办？**

先看 `scripts/dsh-superagent status`。返回 1 可以尝试重启；返回 2 或 3 说明是配置或来源问题，重启没用。再看最新的 `.artifacts/dsh-superagent-*.log`。

**为什么我说了话却没有工单？**

常见原因：这个来源的允许名单里没有你；你的消息没有 @ 到 Agent；主动接单是 `observe`；或者评估判断这不是一个明确的请求。去「触发」和「评估」页面看它为什么被过滤或忽略。

**升级会不会丢数据？**

按文档做备份和回滚不会。不要跳过备份，也不要在有工单运行时直接替换状态目录。

## 8. 已知限制

- 0.5.x，接口和界面还会变。
- 单人、本机、localhost，不是多租户。
- Windows 优先，其他平台验证较少。
- 依赖 DSH 和 Codex 的 alpha 版本。
- 没有生产级的配额、审计导出和告警。
- 中文文档目前覆盖安装和日常使用，架构细节以英文文档为准。
