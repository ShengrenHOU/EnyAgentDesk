# 010 开发与维护原则

本页说明修改这个项目时如何判断归属、控制改动范围和验证结果。具体任务范围以所属 Issue 或 PR 为准。

## 先确定能力归属

| 所属位置 | 责任 |
| --- | --- |
| DSH 宿主与现有插件 | 模型服务、Agent 循环、会话、工具注册、Skills 加载、定时、Web 等通用运行能力 |
| 本仓库 Superagent | 事项身份、授权、工单状态、来源关联、执行器选择、持续跟进及结果交付 |
| Profile 配置 | 选择 bundle 和插件，配置模型、实例、来源及运行参数 |
| 已有 Skills 和专业工具 | 工作方法、领域工具和业务事实 |

修改前先核对现有组件在目标执行路径上的实际能力，再写清已有能力、具体缺口和本次修改位置。组件已安装、已装配、执行器可调用、完整业务流程通过，是四件不同的事实，分别取证。

能够用现有配置解决的问题，直接使用配置入口。新接口必须服务当前真实消费者，不为假设中的未来用途预建抽象。

## 沿现有边界扩展

优先检查现有 Source、Executor、Channel、Policy、Engine 和存储边界。来源扩展参考 [008 Cookbook](008-cookbook.md)，模块责任参考 [007 Architecture](007-architecture.md)。适合现有配置或提示词的需求，沿用其拥有者。

确需改变工单完成标准、授权语义或执行所有权时，在拥有该语义的核心模块集中实现，并检查所有相关入口、旧记录和恢复路径。同一业务判断应有一个拥有者。

PR 说明最终行为，并标明改动属于上游缺陷修复、来源或执行适配，还是本项目自己的业务行为。用有界回归覆盖受影响的行为，尤其是重复事件、中断、重试、停止和升级后续接。

## 维护上游差异

本仓库基于 [dsh-superagent-prototype](https://github.com/deepseek-ai/dsh-superagent-prototype) 演进，作为 DSH bundle 加载。上游升级在独立任务分支进行：

1. 比较固定上游版本和本地差异。
2. 识别已被上游吸收的修复、仍需保留的适配，以及配置或状态迁移影响。
3. 合入后在目标平台跑完整检查，记录实际采用的上游提交和验证结果。

删除自维护实现前，先用实际消费者证明替代路径覆盖了它的行为。上游通用缺陷具备可复现证据时，可以在相应授权下向上游提交修复。

## 代码与依赖

- 未知输入由负责该边界的入口解析和校验，向内部传递明确的领域类型或结构。
- 新增防御分支对应具体可发生的故障、输入合同或安全要求，不为假想状态堆叠空值检查、默认值或兼容层。
- 在承担恢复、错误转换或报告责任的层捕获异常，并保证资源清理。保留根因，不把失败记成成功。
- 不要用 `any` 或连续类型断言掩盖合同错误。缺失是合法业务状态时显式建模；违反合同则在负责的边界明确失败。
- 新增依赖前说明它替代了什么、为什么不使用已有能力，并检查许可证和维护状态。npm 依赖遵守仓库的安装策略。

## 检查与版本

提交前运行：

```sh
pnpm typecheck
pnpm test
pnpm build
```

完整检查是 `pnpm check`。Windows 上的原生子集是 `pnpm check:native`；两者覆盖不同平台，通过一个不代表另一个也通过。

检查通过、构建成功、运行实例激活和消费者可用是分开的状态。报告时说明实际运行了哪些检查、在哪个平台、结果如何，以及没有验证的部分。

版本号在 `package.json` 维护。发布前确认 README、文档命令和实际仓库地址一致；需要激活的运行实例另行完成激活和回读。
